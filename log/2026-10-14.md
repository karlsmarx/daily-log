# 2026-10-14

A performance-testing tool had grown up inside one product's repo, and the goal was to turn it into a portable workbench that could measure any project. The work was mostly separating the generic parts (budget and comparison maths, the UI, the browser and sampling engines) from product-specific constants, and replacing a built-in seed with a project description file that each project supplies. To prove the separation was real rather than cosmetic, a smoke test runs the harness against a small stub app that has nothing to do with the original product. A scope rule was then written down: do one thing well, compose through files and exit codes, and never integrate with outside services. A code-reading audit against that rule turned up a leftover project-specific seed, Linux-only process probes, and some features that had drifted beyond a focused tool. Those were recorded as follow-ups instead of being silently cut.

---

The feature let support staff open a remote device shell in its own window from many different pages, and move an existing terminal into a popup without losing the running session. That meant the server had to support re-attaching to a live session and replaying recent output, and the change needed a schema migration that has to ship before the app. A mutation-testing run showed that a test around an output size cap was too weak: a later small event would still have been recorded after the cap was hit, so the test was tightened to pin that behaviour. After the pipeline passed, a read-through of the release notes found a missing audit event, an intro paragraph that contradicted a later bullet, ragged wrapping, a test-level detail that did not belong, and one claim that had not been seen working on a live system. That last one was flagged as unverified rather than quietly kept.

---

The run details table filtered in the browser, but its bulk actions resolved on the server across the entire run. The result was pagination that did not change when filtering, status pills that showed nothing, and a label claiming a scope that was not the real one. The fix was to move search, status filtering and "problems first" ordering to the server so that they apply before paging, and the actions now act on exactly what the search shows. Retry and cancel were exercised in the browser against the real API, which also showed that an apparent cancel bug was just example data with no queued work. The example-data seeder was updated to create that queue state. One open tradeoff was flagged: the whole-run search re-reads rows on every poll, which is fine at tested sizes but needs watching on very large runs.

---

The question was whether an existing internal alerting platform could deliver fast device health alerts. Reading its docs showed it does rules, cases and history well, but it only sees data after a batch pipeline, so alerts arrive tens of minutes after the event, and sending data more often would not help because the delay is in the pipeline. The alternative explored was to have the device check itself against warn and critical thresholds, send an alert only when one trips, and briefly sample more densely until it clears. Healthy devices then send almost nothing, and aggregating on-device or compacting old data keeps volume down. A separate alert for devices that go silent covers the case where a frozen device cannot report. The existing platform stays in place for trends and ticketing, and the findings were condensed into a short message for a colleague.
