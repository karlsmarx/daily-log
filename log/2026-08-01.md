# 2026-08-01

Debugged a timezone-handling bug in a content-scheduling service where schedules were activating slightly earlier than intended. Traced it to datetime strings being persisted without timezone information — an unlocalized string like `2026-08-01T09:00:00` gets interpreted differently depending on what timezone eventually reads it back, so "intended local time" quietly drifted depending on which part of the system touched it last. Fixed it by localizing before persisting instead of leaving resolution for later:

```ts
// before: ambiguous once read back from storage
const scheduledAt = "2026-08-01T09:00:00";

// after: unambiguous regardless of what reads it back later
const scheduledAt = zonedTimeToUtc("2026-08-01T09:00:00", scheduleTimezone).toISOString();
```

Verified the fix end-to-end through the real data-sync and scheduling-resolution code paths, with the full automated test suite passing afterward.
