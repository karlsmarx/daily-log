# 2026-10-10

An admin console was missing its performance budget because most pages loaded far more than they displayed. List pages read whole registries, the dashboard rescanned millions of rows per visit, and heavy dialogs and pickers mounted on every page load. The fix worked on both sides of the wire. On the server, large lists became paged and searchable, expensive fleet-wide counts moved to short-lived in-memory aggregates refreshed in the background, and a partial index replaced a slow progress query. On the client, identical in-flight requests were shared, a page's requests were prefetched when the pointer rested on its nav item, and dialogs and option lists mounted only when reached. Large CSV parsing moved into a Web Worker so the UI thread stayed free. Each change stayed small and independently reviewable, so a regression could be bisected to one cause.

A long-running performance branch had accumulated merges and reverts, which made it hard to review. I rebuilt it by cherry-picking only the commits that contributed to the target onto a fresh copy of the release branch, dropping each revert along with the commit it undid. Conflicts came from release changes the earlier merge had already reconciled, so each was small, but one touched a layout component and needed care. To confirm nothing was lost or added, I diffed the application code of the new branch against the old one and folded a one-line mismatch into the right commit until the trees were identical. A final type check passed on the rebuilt branch. The fetch step failed, so the rebase used the local copy of the release branch and needs repeating once the remote is reachable. I then grouped the commits by theme and marked fixup and squash candidates as suggestions only, leaving the history rewrite to the author.
