# 2026-09-11

Ran a large adversarial review of an authentication/authorization change using automated mutation testing: deliberately break a piece of logic, confirm the test suite actually catches it, then revert — a way to check that passing tests really pin the behavior they claim to, not just that they run. Split the diff across several parallel automated review agents to cover disjoint areas at once. That surfaced a real process risk, not just code findings: two of the parallel agents happened to touch overlapping files and briefly clobbered each other's uncommitted work — caught quickly via an unexpected diff-stat change, not by luck. Recovered the lost edits and made a deliberate call not to keep running mutating agents concurrently against a shared working tree, finishing the remaining scope sequentially instead. The actual security findings were an over-privileged service account (broader access than the operations it performs actually need) and a missing fail-closed check at startup (a dependency being unreachable should block startup, not silently proceed in a degraded-but-running state).

Diagnosed and fixed several device-telemetry/reporting bugs in a fleet-monitoring backend. One was a MAC-address field that could disagree with itself depending on which of two upstream sources was consulted first — fixed by correcting the fallback order, and mutation testing turned up an uncomfortable fact: the specific ordering that mattered wasn't actually pinned by any unit test, only loosely covered by a broader integration test, meaning the bug could have silently regressed again even with the full suite green. Also closed two "silent false zero" bugs, where a sensor or usage reading being genuinely unavailable was being reported as a real zero value instead of as missing — a real "0" and an absent reading need to stay distinguishable downstream, or a monitoring system ends up alerting on (or ignoring) the wrong thing. Also deduplicated a status/verdict field that was being independently computed and reported from more than one source, which could disagree with itself for the same device.

Stood up a local dev environment for a device-fleet management feature and hit two separate provisioning blockers. One was a templating bug in an infrastructure-automation playbook: a lookup expected an environment variable pointing at a specific file, but with that variable unset it fell back to resolving an empty path, which happened to still exist as a directory — so the error message ("is a directory") pointed at the wrong root cause entirely until traced back to the missing variable. The other was a straightforward access gap: one internal package registry was reachable and working with cached credentials, while a related one returned a permissions error for a repository group cached credentials didn't cover — not a network problem, once actually distinguished from one.
