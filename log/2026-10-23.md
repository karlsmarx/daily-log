# 2026-10-23

The goal was to evaluate how a file-transfer protocol designed for handheld game console Wi-Fi would behave under realistic network conditions, without touching the existing protocol implementation itself. I built a separate benchmarking setup that simulates degraded links (packet loss, throttled bandwidth, added latency) matching the rough capability profile of the target hardware, then ran sweeps comparing a UDP-with-forward-error-correction approach against a plain TCP baseline. The simulated results favored TCP because the simulation doesn't model the handheld's weak CPU and strict in-order packet handling, so the comparison likely overstates TCP's real-world advantage. Along the way I checked whether the server could be deployed on an edge compute platform, and confirmed inbound UDP isn't supported there, ruling it out for the UDP path. I also identified two concrete, low-risk improvements to the UDP protocol: shortening the retry timeout for lost requests (currently idle for a fixed period that's much longer than the measured round-trip time) and pipelining the request for the next data chunk instead of waiting for the current one to fully complete.

For a side project reverse-engineering a low-cost Android TV box, I needed to pull the device tree out of its firmware so a custom Linux build could support all the onboard hardware. The firmware didn't ship with standard device-tree tooling installed, and a quick text-search approach failed because the data is binary, so I wrote a small script to parse the vendor's resource-container format and also scan the other firmware images directly for device-tree headers. That turned up two copies of the same tree, which I decompiled into readable source and flagged that the result can't be used as-is with a stock Linux kernel since it still has vendor-specific entries. Separately, the physical unit had a wired network port that showed no link lights and no connection in the installed OS. I walked through a structured diagnosis: ruling out the cable/router first, then separating an OS-detection problem from a hardware failure by booting the device's stock factory OS to see if networking worked there. That test stalled because the device hung at a boot screen; I set up a watcher to grab logs over a debug USB connection as soon as the device became reachable, but it timed out waiting for the device to appear, pointing back to a cabling or port-selection issue on the debug connection rather than the device itself.
