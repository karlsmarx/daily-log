# 2026-07-24

The group-ownership approach from the last two days worked, but testing it against a closer-to-production host surfaced a problem with the underlying mechanism, not just the specific rules: changing a file's group ownership (`chgrp`) replaces whatever group access was there before. On a shared production host where other tooling might already depend on a file's existing group, that's a silent way to strip access nobody asked to have removed — it just happens to be safe in a clean container image with no prior state.

Redesigned around POSIX ACLs instead, which add an access entry without touching what's already there:

```sh
# before: replaces the file's group wholesale
chgrp device-ops /var/lib/device-agent/state.db

# after: adds an entry, existing ownership and other ACL entries are untouched
setfacl -m g:device-ops:rw /var/lib/device-agent/state.db
```

That distinction — additive vs. replacing — was the actual point of the redesign, not the specific tool used. Also tracked down and fixed a container build bug where filesystem ACLs weren't persisting across image layers (Docker's layer-squash was dropping the extended attributes ACLs live in), and validated the fix by exec'ing into a running test container and checking `getfacl` output directly rather than trusting the build log.
