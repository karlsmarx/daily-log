# 2026-09-07

A teammate stress-testing a security config flag found a fail-open bug in its parser: the flag accepted boolean-ish values, but the parser only recognized a fixed set of exact tokens, and silently fell back to "disabled" on anything else — a stray number, a typo'd string — with no warning anywhere. Fixed it to fail closed instead (treat an unrecognized value as the safer state and surface a warning) rather than fail open. While fixing it, found the identical parsing defect on a sibling security-related flag and had to make a judgment call rather than applying the same fix blindly: that second flag had a documented reason for defaulting to its permissive state (forcing it to the strict state on a bad config value risked breaking a legitimate device that depended on a related check never having been confirmed safe to enforce), so it was deliberately left fail-open while the first flag was made fail-closed. Not every fail-open flag is a bug — some are a considered availability/security tradeoff, and the fix has to preserve that distinction rather than "fixing" both the same way. Added a status-endpoint signal (booleans only, never the raw config value) so a misconfigured flag is now visible without needing to read logs:

```ts
type SecurityFlagValue = boolean | string | number | undefined;

function parseSecurityFlag(raw: SecurityFlagValue, failClosed: boolean): { value: boolean; recognized: boolean } {
  if (typeof raw === "boolean") return { value: raw, recognized: true };
  const s = String(raw ?? "").trim().toLowerCase();
  if (["true", "1", "yes", "on"].includes(s)) return { value: true, recognized: true };
  if (["false", "0", "no", "off", ""].includes(s)) return { value: false, recognized: true };
  // unrecognized: fail to the safer state for *this* flag, not a blanket default
  return { value: failClosed, recognized: false };
}
```

Also designed and implemented an async, batched row-validation pipeline for a CSV bulk-import wizard: instead of a Web Worker, it yields to the event loop between chunks so validating a large file doesn't freeze the UI, without the complexity of actual threading. Reworked the diff/edit review UI for clarity and accessibility, and replaced sequential per-row API writes with batched transactional writes. Review turned up a real race condition in single-row re-validation after an edit — re-editing a row while its previous validation call was still in flight could let the stale response land after a newer one and silently overwrite it — fixed with an identity check so a stale in-flight result is discarded instead of applied; also fixed a misleading error-reporting path where a field-name collision in the row's metadata masked the actual validation error shown to the user.
