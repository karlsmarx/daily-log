# 2026-08-27

Diagnosed a race condition in a device management UI where a device would fail to disappear after being unbound: a stale row was sticking around and blocking deletion. The underlying pattern was check-then-delete — look up whether the row exists, then delete it in a second step — which leaves a window for something else to change state in between. Replaced it with a single atomic delete instead of two round-trips:

```sql
-- before: read, decide, then act -- a window for the row to change underneath you
SELECT id FROM device_bindings WHERE device_id = $1;
-- ...application decides it's safe to delete...
DELETE FROM device_bindings WHERE id = $1;

-- after: one statement, no window
DELETE FROM device_bindings WHERE device_id = $1 RETURNING id;
```
