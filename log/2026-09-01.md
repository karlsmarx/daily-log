# 2026-09-01

Worked through code review feedback on a backend service's error handling for a client-abort edge case: an in-flight request that got aborted mid-wait could leave the handler parked indefinitely instead of cleaning up, because the abort signal was only checked at one point instead of on every relevant event. Fixed by settling the wait on both the expected completion event and on close/abort, with a regression test that reliably hung without the fix. While in that code path, also replaced a flat 500 response on a read path with typed error codes, so a handful of genuinely different failure conditions (malformed input, an already-modified record, an unsupported type) each report the right status instead of collapsing into one generic error — and consolidated a duplicated "wait for readiness" mechanism, which had been reimplemented in two places as a polling loop, into one shared implementation backed by a single resolved-once promise, after checking every caller wasn't relying on the polling behavior itself:

```ts
class ReadyGate<T> {
  private resolveFn!: (value: T) => void;
  private promise = new Promise<T>((resolve) => { this.resolveFn = resolve; });

  set(value: T) {
    this.resolveFn(value);
  }

  get ready(): Promise<T> {
    return this.promise;
  }
}
```
