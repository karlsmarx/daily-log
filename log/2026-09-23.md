# 2026-09-23

The engineer was asked to thoroughly review a merge request that changed how a scheduling/launch feature selects target devices. Rather than reading the diff alone, they checked out the branch with isolated databases, drove the real UI with browser automation, and let scheduled jobs actually fire to observe outcomes instead of just inspecting code. That surfaced a regression worse than first suspected: after a recent migration, essentially every scheduled job failed when it ran, because a field meant to hold a list of device identifiers was being stored as the literal text "undefined" and misread downstream as valid data. They also found a permissions inconsistency where one part of a flow required an authorization grant that a related action in the same flow didn't check for, a naming collision where two different tags produced the same generated identifier, and a database error triggered by an older migration during a specific deploy path. Every finding was verified by reproducing it against a running instance, and the results were left as pending review comments rather than published immediately, so the original author could act on them first.

The work extended serial and network control of display panels to additional hardware vendors. For one new vendor, the engineer mapped an existing generic on-screen-display toggle to that vendor's equivalent low-level command, but declined to guess at other feature mappings where the vendor's documentation didn't clearly specify an equivalent, flagging them for follow-up once a real device could confirm behavior. They also answered a design question about whether panels from different vendors could share one physical serial connection: each panel already opens its own logical connection with its own communication speed and driver, so mixed-vendor setups on separate ports work fine, but chaining different vendors on a single shared line does not, both because of speed mismatches between vendors and because it's unverified how one vendor's device reacts to another vendor's message framing. They noted that only two of five supported vendors had been validated against real hardware captures, with the rest tested only against simulated responses, and recommended bench testing before relying on the untested paths. Separately, they walked through the internal steps to get a build published to a test channel through the CI pipeline, clarifying which manual pipeline step was safe to use for testing versus one intended only for reviewed, released builds.
