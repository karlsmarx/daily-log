# 2026-07-22

Spent the day tightening how a service-manager component was allowed to touch the host. It had been running its build and provisioning steps with broad, implicit privilege — anything that could `sudo` at all could do anything — and the goal was to cut that down to exactly the operations it actually needs. Landed on a dedicated system group for file ownership plus a narrow sudoers rule scoped to specific commands, rather than broad root access:

```sudoers
# /etc/sudoers.d/svc-agent — narrow the agent to the two operations it needs
Cmnd_Alias SVC_RESTART = /usr/local/bin/svc-ctl restart *
Cmnd_Alias SVC_STATUS  = /usr/local/bin/svc-ctl status *
svc-agent ALL=(root) NOPASSWD: SVC_RESTART, SVC_STATUS
```

Rolling this out surfaced a separate bug: a container volume mount was overwriting the file permissions baked into the image at build time, silently reverting the new group ownership every time a container started. Root cause was mount ordering — the mount landed after the image's baked-in `chown`, not before it as assumed. Fixed by re-asserting ownership in the entrypoint after the mount runs, instead of relying on it surviving from the image layer.

Also investigated and resolved a dependency-leakage issue in a monorepo by extracting a reporting/plugin subsystem into its own independently buildable package, decoupling it from a larger application's framework and database dependencies; and worked through credential-handling issues in an internal provisioning/testing tool.
