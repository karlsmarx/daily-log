# 2026-07-09

Added a headless auth path to a device-provisioning CLI so it no longer needs a browser-based approval step for every run. While doing that, found and fixed a regression from an earlier merge that had silently dropped a fleet-detection check, and separately noticed a newly extracted library mostly duplicated code that already existed elsewhere in a more current form.

Also added audit logging to a provisioning API, so requests that get ignored or modified by validation are actually recorded and surfaced to the caller instead of disappearing silently — a caller that got a request "changed out from under it" had no way to know that before. A generic version of the pattern:

```ts
async function handleProvisionRequest(req: ProvisionRequest) {
  const { value, changes } = validateAndNormalize(req);
  if (changes.length > 0) {
    audit.log("provision.request.modified", { requestId: req.id, changes });
  }
  return apply(value);
}
```

Verified with a full test suite at 100% coverage, and confirmed there was no redundant build work between two related build paths.

Reviewed the security model of a new internal provisioning API more broadly — secret handling, rate limiting, a missing audit trail — and discussed mass-rollout scenarios. Concluded that the current shared-secret transport step is a reasonable starting point but should eventually be replaced with per-device public-key authentication, since a shared secret's blast radius on compromise is every device that holds it, where a per-device keypair's blast radius is one device.
