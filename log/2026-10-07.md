# 2026-10-07

I took a QA report of UI and permission bugs written against an older release line and checked each one against the newer line before planning anything. One critical claim, that a read-only user could write to a module, did not reproduce on the newer branch, so I flagged it for retest instead of patching it. Of the rest, a few were already fixed or waiting on an unpublished dependency, and those I left alone. The remaining ones I fixed on a separate worktree: some write actions were still reachable by read-only users, and I closed those on both the API and the UI, with disabled controls and a short explanation. Dialogs also showed a search total instead of the number of selected rows. The last change was making a manual column mapping apply to the current import only, with an explicit opt-in checkbox to save it as a reusable rule. I added tests for the permission checks and the opt-in behavior, then broke each fix on purpose to confirm the tests fail without it. Typecheck, lint and the frontend suite pass. The only backend failure was an end-to-end file that depends on a live local server, so it isn't caused by these changes. Nothing was checked in a browser yet.

---

This was a performance pass against a dataset about eight times larger than normal, and the first job was rebasing a long series of commits onto a newer release line. Most applied cleanly. One conflicted because upstream had touched the same paging code, so I read what upstream had changed and merged the two before continuing, and I committed the in-progress work first so nothing was at risk. The changes themselves were mostly about not doing work up front. Large lookup grids and a long list now page, filter and sort on the server. Repeated identical requests are shared while in flight. Expensive fleet-wide counts are served from short-lived in-memory aggregates that refresh in the background and are cleared by the app's own actions. Dialogs only mount, and so only fetch, when opened. Hovering a nav item now prefetches the requests its page will make. To judge whether any of this helped, I ran a browser-driven sampler over every route on the new baseline, reporting p50 first-draw times. One early finding was that hovering before a click made one page slower, which suggests prefetch competes with the page's own load there, so I noted it for follow-up. When the sampler hit a navigation timeout, I checked that the server was healthy with no stuck queries, treated it as a transient stall, and made the sampler tolerate it. I deliberately did not edit the shell script that was running, since bash reads scripts incrementally and an edit could corrupt the live run. The baseline was still in progress at the end of the session.
