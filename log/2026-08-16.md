# 2026-08-16

Built out a migration framework for a SQLite-backed data layer and integrated it into a clustering service. The interesting bug here was ordering: migrations were applied in the order they were discovered on disk, not a guaranteed order, so a partial failure partway through could leave the schema in a half-configured state with no reliable way to know which step it had actually reached. Fixed it by applying migrations strictly in version order and recording the last successfully-applied version in the same transaction as the migration itself, so a crash mid-migration either commits cleanly or rolls back to the last known-good version — never something in between:

```sql
BEGIN;
-- migration body for version N goes here
UPDATE schema_meta SET applied_version = N WHERE applied_version = N - 1;
COMMIT;
```

If the `UPDATE` doesn't happen, the whole transaction rolls back, so `applied_version` and the actual schema state can never disagree.

Code review judged the work not yet ready to ship, pending a package release and some remaining integration work — a reasonable call, and better caught in review than after. Also resolved merge conflicts (including a credential-security cleanup that had drifted between branches), fixed flaky CI tests caused by unmocked module loading, and tuned default memory limits to bring down local test resource usage.
