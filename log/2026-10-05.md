A CI pipeline was failing on a feature branch's merge request while the same commit passed fine when pushed directly to a branch, which was confusing since nothing in the code looked related to the failing test. Comparing the two pipeline logs side by side, the key clue was a large chunk of buffered test output whose displayed timestamps lagged several minutes behind the timestamps embedded in the test output itself, and the job died mid-run without ever printing a final summary -- a classic signature of a job being killed by the CI runner for resource exhaustion rather than failing an actual assertion. The fix was simply to retry the job, which passed cleanly once rerun, confirming the pipeline failure was an infrastructure fluke and not a real regression. The merge request pipeline was re-verified to pass fully afterward.

A code reviewer flagged that a memory-leak fix for a log-parsing routine only addressed part of the problem: the routine read a large file in fixed-size chunks to avoid holding the whole file in memory, but every time a line matched a pattern of interest, the match was stored as a substring taken directly from the chunk. In the JavaScript engine used here, a substring like that doesn't copy data -- it keeps a reference back into the original chunk, so any chunk containing a match stayed resident in memory for the life of the operation, undermining the original memory fix whenever matches were reasonably frequent. Benchmarking with a synthetic multi-hundred-megabyte file confirmed the problem was real and density-dependent, and also showed that limiting the number of retained matches alone wasn't enough -- explicitly copying each matched line out of its backing chunk was what actually kept memory flat regardless of how many matches occurred. A second question came up during review: did chunked reading introduce a risk of silently losing or splitting lines that straddled a chunk boundary? Tracing the read logic by hand found the file-offset handling was correct, and a differential test comparing chunked parsing against a naive whole-file scan across many file sizes and explicit boundary-straddling cases confirmed no lines were lost, duplicated, or reordered. The tests were also mutation-tested -- deliberately broken to confirm they would actually fail if the bug came back -- before the full suite was run clean.

```js
// before: substring keeps the whole backing chunk alive in memory
function onMatch(chunk, line, matches) {
  matches.push(`${line}`);
}

// after: copy the bytes out so the chunk can be garbage collected
function onMatch(chunk, line, matches) {
  matches.push(Buffer.from(line).toString());
}
```
