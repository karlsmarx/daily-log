Investigated a potential concurrency risk between a background daemon and other local tools that all read and write the same single-file SQLite database. Enabling write-ahead logging with a busy timeout absorbed most of the contention, but that alone doesn't stop two independent tools from racing to do the same "first run" setup work on a fresh database. Added an explicit guard for that case — a short-lived advisory marker so a second concurrent starter backs off instead of duplicating the setup:

```python
def try_claim_setup(conn):
    try:
        conn.execute("INSERT INTO setup_lock (id, pid) VALUES (1, ?)", (os.getpid(),))
        return True  # we're the one doing setup
    except sqlite3.IntegrityError:
        return False  # someone else already claimed it
```

Added tests that start two processes against the same fresh database file and assert only one of them ever runs setup.
