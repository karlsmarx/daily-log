# 2026-09-13

Debugged a build failure in a personal embedded/console homebrew project down to three separate bugs stacked on top of each other, not one: a Makefile that never referenced a library its own source now depended on (so a header simply couldn't be found), a couple of genuine typos/nonexistent constants in that new source file, and — once the code actually compiled — a link-time failure from a classic C/C++ mismatch: a C source file included into a C++ file without an `extern "C"` guard, so the linker looked for a C++-mangled symbol name that the C compiler never produced:

```c
// wifi.h — without this guard, a C++ translation unit that includes
// this header expects a C++-mangled symbol; the .c file exports a
// plain C one, and the linker can't match them.
#ifdef __cplusplus
extern "C" {
#endif

void connect_to_saved_wifi(void);

#ifdef __cplusplus
}
#endif
```

Separately, tracked down why `printf()` was producing no visible output at all despite the build succeeding and the program running: on this platform, standard output isn't wired to anything by default — a console target has to be explicitly initialized before the first print call, and nothing in the codebase did that. Confirmed by grepping for every known console-init entry point and finding none, rather than guessing. Left it unfixed as asked (this was a "diagnose only" request), but the actual fix would need to pick an unused display layer for the console output and initialize it before any code path that prints, since forcing the platform's default console setup can silently reset unrelated video-mode configuration already in place.
