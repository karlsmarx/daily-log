# 2026-09-18

Revisited a QA report where a file-upload feature silently rejected every valid upload. Watching the actual network request during a live retest showed the client was sending an empty JSON payload instead of packaging the file as a multipart form submission, meaning the file's bytes never actually left the browser. That explained why the server behaved as if nothing had been submitted at all. The likely fix — switching the upload request to a proper multipart form — was identified and documented, but left for the next person to implement and confirm.

A reported broken link sent users from a device list into a page that no longer existed. Investigation traced the likely cause to an earlier rename of a major navigation section: a link built relative to its current page location kept pointing at the old path structure instead of being updated for the new one. This diagnosis was written up for follow-up rather than fixed in this pass.

A cosmetic bug made every notification toast in an app appear twice, stacked in different corners of the screen. The cause was the app mounting its own copy of a notification component that the surrounding platform shell already provided globally for every app — both instances listened to the same underlying event stream, so each toast fired twice. The fix was removing the app's redundant instance, confirmed live by checking the notification rendered as a single element instead of two.

A loading-state bug made a screen briefly display a "nothing selected, zero results" message immediately after a valid selection, indistinguishable from a genuine empty result, until real data replaced it a few hundred milliseconds later. The cause was that old state from before the selection wasn't cleared when the selection changed, so it lingered on screen through a debounce and network round trip. The fix cleared that stale state immediately on selection change, scoped narrowly so it wouldn't cause flicker in unrelated parts of the same form. Verified live by rapidly sampling the screen during the transition window and confirming the misleading text no longer appeared, backed by the existing automated test suite passing.

Several standalone prototypes were built first — a riddle game, a timed word-spotting game, a branching dialogue quest, and a trivia quiz — each self-contained with its own simple result-reporting hook so it could be tested independently. This continued a hardware-integration feature for remotely powering on and controlling display screens over a network, building on drivers added earlier in the same effort. The main addition was a network transport layer and a Wake-on-LAN packet sender, plus config validation for the new addressing fields needed per screen. A real bug surfaced in the Wake-on-LAN code — a network socket needed to be bound before enabling broadcast mode, a detail an internal default in the original send routine had been masking. It was found by rewriting a test to exercise the real function instead of duplicating its internals, and fixed properly rather than papered over. The change also corrected a stale rejection that had assumed one brand of display couldn't be reached over IP, now that a real network transport existed for it. Transport tests were verified against a real local TCP server, the full regression suite and linting stayed clean throughout, and the work was committed as the final step of a previously planned multi-step effort — with one remaining piece (a live capture against real hardware for two drivers) still blocked on unrelated environment access.

A run-orchestration feature originally advanced a whole batch of devices through a sequence of steps only once every device in the batch had finished, so one slow or failed device held up everyone else. It was redesigned so each device advances independently the moment it finishes its current step, with failures affecting only that device; devices that finish a step late are folded into an already-started run for the next step rather than waiting for a fresh batch. Along the way, several other issues were fixed: an error path that misattributed a database outage to bad user input, a race condition that could let multiple server instances double-dispatch the same work (closed with an advisory lock matching an existing pattern elsewhere in the codebase), and a pair of redundant safety checks that each made the other untestable — one was removed once mutation testing proved the remaining check alone was sufficient. The new logic was verified with unit tests against fakes and a battery of deliberately introduced code mutations, all of which were caught; it was noted explicitly that the hand-off between steps hadn't yet been exercised against a real, successful multi-device run, since the local test environment can't produce one.

A downstream change introduced stable identifiers and versioning for a set of shareable content bundles, and this work updated a template-saving feature to track bundles by that new versioned identifier rather than a raw version string. Templates now pin a bundle id per step, while the human-readable version and grouping name are resolved fresh on every read instead of being stored, so they always reflect current state. Listing endpoints were changed to group multiple versions under one shared identifier for a picker UI. During a rebase onto shared history, a subtler bug surfaced: a database migration had been renamed, which changed its internal tracking key and caused it to be treated as brand new and re-run against a database that already had the table — fixed by making the migration idempotent, matching an existing convention already used elsewhere in the codebase. Separately, an ad hoc smoke-test script accidentally damaged local seed data by renaming an entity and then failing to undo the rename because of a uniqueness constraint on the old name; the corrupted state was repaired by hand, and the script's risky step was made explicitly opt-in with a warning that the action is irreversible.

A merge request's pipeline was failing for two unrelated reasons: a frontend type error from a component prop that didn't exist on the receiving component, and a backend dependency-injection test that broke because a newly added service required a database connection the test's stub container didn't provide. Both were straightforward fixes once isolated. Separately, a static-analysis security scanner flagged a medium-severity finding in the same change: two client-supplied string fields used to tag an uploaded content bundle had no format restrictions, and one of them was later used to build a filesystem path when resolving that content — meaning a crafted value could include path-traversal characters and cause the server to read arbitrary files off its own disk. The fix added strict allow-list validation to reject anything but simple identifier characters in both fields. New regression tests were added and mutation-tested — confirmed to fail without the fix and pass with it — which is a basic but effective way to prove a security fix actually does something rather than just looking plausible.

A UI feature branch needed updating for a backend contract that had changed significantly since it was created: instead of picking a version directly, users now first pick a stable named group, then a version within it, with a separate fallback path for content that hasn't been assigned a name yet. While rebasing, it turned out the target branch had already gained its own, more advanced version of the same contract, added independently under a very similar description — so the work became reconciling with that existing implementation rather than introducing a new one. Because the branch had originated as another engineer's work that had since been modified locally, care was taken to preserve correct authorship: the original UI commit was reconstructed and committed under its original author's name, with only the actual contract-adaptation work attributed to the current author, keeping credit accurate despite the mechanical rewriting of git history.
