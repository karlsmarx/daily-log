# 2026-10-20

A status banner in an internal operations dashboard was flashing a "finished" state based on a client-side absence-of-pending-work check rather than the backend's actual completion flag, creating a window where an unfinished unit of work could appear done. The fix was to gate the banner directly on the server-derived completion flag. Separately, a secondary text color token was audited against WCAG AA contrast ratios across several background surfaces; the light-mode value failed on one surface, so it was darkened and scoped to light mode only, leaving the dark-mode value untouched. Verified with the full UI test suite, type checking, linting, and mutation testing targeting both changes specifically.

A multi-phase feature design went through structured review, and specialist reviewers raised seven open questions about an aggregation model — things like when a top-level status should flip to "done," how to detect a regression after something was marked resolved, how to group recurring background jobs into one logical unit for display and export, and how a display cap should interact with that grouping. Most were resolved by working through the implications of the model already chosen, rather than opening new design space. One question turned out to rest on an incorrect assumption in the design document about an existing integration point, and that assumption was corrected. The result was a finalized design document and a handover brief with explicit notes marking these decisions as settled, so a following work session wouldn't re-litigate them.

Traced a feature's actual behavior against its stated product goal — letting someone follow a multi-step operational process from first failure to final report in one screen — by reading the backend code, UI code, and specs directly rather than trusting existing documentation. The underlying per-item tracking logic was genuinely built, but the stated goal wasn't fully met: the search box was running in free-text mode instead of the structured scope-and-value filter mode used elsewhere in the product, and there were two separate, overlapping views where the rest of the product used one combined grouped table. The fix was to switch the search component into its existing builder mode and merge the two views into a single table grouped by location, with roll-up counts and per-group collapsing, matching a pattern already used on another screen in the same app. The feature's top-level concept was also renamed to avoid colliding with an existing, differently-scoped term already used in the product, with the rename propagated across the UI, an API route, and an integration surface. Verified with full type checking, the full UI test suite (over 2,700 tests), the relevant backend suites, and a recorded screen walkthrough.

Commissioned an independent adversarial review of a shipped operational dashboard feature, instructing the reviewer to use the app as a real end user first and to treat the author's own documentation and commit messages as unproven claims. The review surfaced fourteen issues. A search field was silently capping suggestions at a fixed count, hiding real results on large datasets. A downloadable report mislabeled an item that had regressed after being marked resolved as simply "still failing." A report's completion timestamp reflected download time rather than when the underlying work actually finished. A destructive bulk action had no confirmation step before executing. A particular job type that completes without further action wasn't being recognized as finished, so the UI kept offering actions meant only for active jobs. Accessibility gaps were also found (missing table semantics for screen readers), along with mobile layout clipping on action buttons and a "filtered" report download that silently ignored the active filter and exported everything. Each was fixed at its source: status computation was consolidated into one canonical function reused everywhere, timestamps were derived from the latest actual event instead of wall-clock time, the missing confirmation dialog was added, the completion check was extended to cover the missed job type, proper ARIA table roles were added, the responsive CSS was corrected, and the export query was extended to respect the active filter. Verified with full backend and frontend regression suites plus manual checks against the running app via its API and page content, including disclosing (rather than silently fixing) an earlier reviewer's accidental state-changing action left in the shared demo environment.

Addressed two major findings from an internal review of an operations-tracking feature. First, different parts of the UI were counting the same underlying failures differently under similar-sounding labels, so the same number meant different things depending on which screen you were looking at; the fix standardized every surface to compute and phrase the breakdown the same way. Second, a tracked batch of work items could never reach a "finished" state if even one item was permanently unresolvable, with no way to deliberately exclude it; a workflow was added to explicitly leave an item out with a required reason, recorded as an audited, permission-gated, reversible record, available either one at a time or in bulk with a safeguard preventing already-fixed items from being swept in by accident. Verified with mutation testing on the new logic: 20 injected mutations, 17 caught immediately, and the 3 that survived (gaps in an export file and in a bulk-action count) were each given a new test and are now caught, alongside full regression suites before committing.

Wrote a roadmap document tracing a feature's planned evolution across four stages: first establishing basic links between related units of work, then giving an end user a single screen to track and act on them, then enabling a final audited report, and finally making the system infer relationships automatically instead of requiring manual linking. The document also captured ground rules for the effort, including that outcomes already computed should never be silently rewritten, that a remedial action only counts as resolving a problem if the system can verify the real underlying check actually passed, and that no new grouping concept should be introduced without evidence the existing ones are insufficient.
