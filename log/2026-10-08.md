# 2026-10-08

The question was whether automation could expose an interactive shell to a browser for fleet devices. Tracing the existing flow showed that the devices already accept SSH connections from the automation runner, so nothing new is needed on the device. The missing piece is a browser-to-SSH bridge, and it belongs on the server side. I looked at an existing browser terminal in a sibling project as prior art for the wire protocol and UI. The plan covered how the bridge would reach devices behind intermediate hops, how to authenticate a long-lived socket, how to survive load-balancer idle timeouts and deploys, and how to audit sessions. I stopped at a reviewed plan and wrote no implementation.

The ask was for ideas to improve reporting, checks and operational speed in an internal fleet-migration console, with comparisons to well-known external products. I surveyed what the product already had, then measured each idea against it so the proposals built on existing parts rather than starting over. The ideas covered a richer device panel, remote actions with a concurrency budget and an error-threshold circuit breaker, drift detection, live fleet queries, a rehearsal and rollback lifecycle for cutovers, and a hand-off to field operations with an evidence pack. I ordered them by cost and risk reduction. Cheap, visible wins on existing backend capability came first, and the riskiest interactive capability came last. I also flagged one open question I hadn't verified: whether a tested revert flow already existed.

---

The goal was to keep device facts in sync automatically with data that a scheduled CI pipeline already produces. I used the GitLab CLI to find which project and job generate the artifacts and where they are stored. We had no access to one environment's store, so I confirmed the storage pattern from the other environments instead. I then added the sync to the app and a read-only, narrowly scoped access grant in the infrastructure code. Before committing I checked that the new config value actually reaches the running service and that the per-environment resource names resolve correctly. Terraform wasn't installed locally, so formatting and validation fall to CI. I also noted two things that need a human before merging: agreement from the team that owns the data, and a check of the production store's policy.

A QA report listed a mix of bugs, and the first job was to find which were still present on the newest release branch. I fixed a misleading count in a bulk-action dialog, a duplicated-parentheses label, a broken redirect on access denial, fields that were saved but never shown, and a case where manual column mappings were silently saved as reusable rules. That last one is now an explicit opt-in. I also closed an authorization gap. Midway I realized I had matched the wrong two fields to the QA description, so I re-read the reproduction steps and re-verified each item against them. A new Tags column went in with one batched fetch per page, and the CSV export fills it so it doesn't come out blank. Typecheck and the frontend tests pass, and the backend tests pass apart from a live-server test that fails because the local server runs an older build.

---

The work was a measured performance pass over a data-heavy admin console, with one pain point at a time, worst first, and each change tested against a baseline. Moving parsing and lookup work off the main thread's critical path cut the import upload step from about 3.2 s to 0.5 s. Validating rows was the next worst at about 9.4 s, now about 2.6 s. For a further round I profiled the validation step in isolation, then replaced per-row accessor overhead and a slow time-zone check with cheaper equivalents. Each change was kept only if it got closer to budget. Other changes this period moved long lists to server-side paging and short-lived in-memory aggregates, and a read-only audit ranked the remaining server work by load. One result was a small honest caveat: a single row got slower at median, but with ten samples that is within noise, so I didn't count it as a win. Specs, lint and rebuilds were run for each change.
