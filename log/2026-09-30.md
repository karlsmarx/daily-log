# 2026-09-30

A set of device-automation playbooks for checking and toggling display power state had a bug where a device that was simply unreachable over the network produced the exact same "no outputs found" error as a device that was reachable but genuinely had no displays configured — because the parsing logic only ever looked at command output and quietly treated a missing connection the same as empty output. The fix added an explicit reachability check up front so the two failure modes report distinct, accurate messages. While building out the broader playbook set, testing against a fake CLI (rather than relying on syntax-checking alone) surfaced three more real bugs: a stray stray quote character that silently turned a templated dictionary into a string, a misplaced configuration key that made a safety check a silent no-op, and an assumption that two values set in the same automation step could reference each other, when the framework actually evaluates them independently. All were fixed and verified against simulated hardware covering normal reads, missing capabilities, on/off mutation, and a vendor-specific fallback path.

---

A deployment pipeline used a timer-arming command flag that wasn't supported on some older lab devices, and because the failure was silently ignored, the state tracking never updated correctly after a timeout — the fix dropped the unsupported flag and made the failure visible as a warning. Separately, the failure-classification step used a regex that could match the wrong category first, and some verification failures produced no classification at all; the fix reordered the matching and added a fallback "unknown failure" category so every failure is always labeled. A rollback path also read back a state file that could be malformed, which previously caused a crash; it's now treated as empty if invalid. Lastly, an error-reporting path could echo back sensitive command output when a task failed, so logging was suppressed for that case to match the sensitivity of the original task. Documentation claiming a device always reboots and rearms after rollback was corrected — that behavior is actually opt-in and off by default — and timeouts were added to pipeline stages that previously had none.

A UI review comparing the current interface against a design reference found that one informational badge — meant to tell the user that a failure in a run stops downstream steps for a device — was fully implemented but had been commented out, so it silently stopped rendering. Restored it and confirmed with the full type-check and automated test suite (over 1400 tests) that nothing else regressed. A broader design-consistency review of the related screens found no other concrete issues worth changing.

---

A scheduling feature supported creating and cancelling jobs but had no way to edit them, so that capability was added following the existing CRUD conventions in the codebase. Along the way, two UX issues were found and fixed: submitting a scheduling action didn't navigate away or clear its form state afterward, so a user could accidentally double-submit, and a required field on the creation form wasn't enforced consistently on the edit form. A follow-up effort added structured, paginated search/filtering over the scheduling data, including filtering on nested list fields, which required extending the underlying query-building logic to support filtering directly on an array-type database column rather than just an array nested inside another field. Manual end-to-end testing against a real database surfaced three further bugs: a missing type cast for a JSON column stored as text, a special sentinel value from the data layer breaking that cast, and large integer identifiers not being converted correctly from the database driver's string representation, which produced invalid dates in API responses. All were fixed at the root and verified with the full backend and frontend test suites plus live manual testing.

A report came in that downloading a zip of run artifacts for a very large run was timing out and showing a garbled error. Investigating with a real authenticated browser session (not just a command-line request) showed the download endpoint, authentication, and streaming logic all worked correctly — a large zip actually downloaded successfully in a reasonable time. The actual problem was in the test fixture used to simulate a large run: it padded the synthetic data with a single repeated character, which compresses almost to nothing, so the test zip looked "suspiciously small and fast" rather than representative of a real near-capacity transfer. Switching the fixture to generate randomized, less-compressible padding made the test accurately reflect real-world download size and timing, confirming there was no actual product bug.

A continuous-integration test suite started failing after a prior commit passed a component prop that was never actually declared on the receiving component — harmless at runtime since unknown props are silently ignored, but it broke a stricter type-check path used only during the test compile step, not the main build. Removed the dead prop, confirmed no behavior changed, and the full test suite passed again. The work also involved two rebases onto a moving release branch, resolving a handful of merge conflicts by keeping both sides' legitimate additions, with lint, build, and full test suite (1400+ tests) verified clean after each.
