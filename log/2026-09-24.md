# 2026-09-24

A device in a hardware-control system was failing to respond to power and status commands even though it was correctly wired and detected by the platform. Digging into the logs showed the driver was sending commands formatted for one display vendor's protocol while the actual panel, once probed directly over its serial line, answered to a different vendor's protocol entirely — the panel had been physically replaced at some point but the software configuration was never updated to match. The fix was reconfiguring that one device's driver type to match the panel actually installed, then verifying the read and power commands worked against it. Since the underlying config file couldn't be trusted as a source of truth for which hardware was really present, I also proposed a follow-up check that probes each port with both protocols and lets the panel's own reply determine its type, rather than trusting the static config. To make the findings reusable, I wrote up a plain-language QA test guide covering setup, panel identification, and power/read verification, including known limitations of the current build so testers wouldn't mistake them for new bugs.

The most interesting part was the commit hygiene at the end: several logical changes lived in files that also had unrelated modifications, including one in a separate submodule pinned to a specific commit. To keep the change history clean, I staged partial, in-between snapshots of the affected files so each commit represented exactly one logical change, and re-ran the relevant test suite against each staged snapshot before committing rather than trusting the full working tree. I also caught and reverted an unintended auto-formatter change that had crept into an unrelated file during a lint run, and confirmed via full build, typecheck, lint, and test runs (with known environment-driven flakiness ruled out by rerunning failing tests in isolation) that nothing was broken before committing.
