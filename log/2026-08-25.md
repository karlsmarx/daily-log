# 2026-08-25

While generalizing a database ORM adapter to support multiple database engines, hit a race condition in the adapter's distributed lock-release path: two holders could each believe they held the lock across a slow release, because "release" only checked that a lock record existed, not that the record still belonged to the process releasing it. A lock acquired, then lost to a timeout, then re-acquired by someone else, could still be released by the original (now-stale) holder — deleting a lock that wasn't theirs anymore.

Fixed it with a fencing token: every acquire gets a strictly increasing token, and release (and any write made "under" the lock) must present the token it was issued, so a stale holder's release or write is rejected once a newer holder has taken over:

```ts
async function acquire(key: string): Promise<{ token: number }> {
  const token = await db.incrementAndGet(`${key}:fence`);
  await db.setLock(key, token);
  return { token };
}

async function release(key: string, token: number): Promise<void> {
  // only release if this token is still the current one -- a stale holder
  // whose lock was already reassigned is a no-op, not a bug
  await db.releaseLockIfCurrent(key, token);
}
```

Validated the fix against real database containers with a full regression suite, including a test that deliberately stalls one holder past a lock timeout to force the stale-release case.

Also added filtered log-viewing support for in-process service plugins to an internal CLI tool, and replaced a buffered subprocess read with a streaming implementation to remove a memory ceiling on large logs.
