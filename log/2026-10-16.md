Reviewed an investigation into high CPU usage on an embedded display device, where a UI animation was suspected of causing sustained near-100% load on all cores of a small multi-core system. The existing fix removed the animation and showed a large drop in measured CPU usage on one lab unit, but the evidence only covered that single device, so part of the review was checking whether the fix generalized and whether the supporting data and write-up were still safely recoverable in version control. The deeper technical question was why removing one animation helped so much on a multi-core machine: profiling showed the rendering work for each frame passes through a fixed sequence of single-threaded stages (page rendering, compositing, rasterizing, GPU command submission, and display presentation), and since no single thread can span multiple cores, one heavily loaded stage shows up as a pegged core even while others sit idle. Removing the animation stops frames from being generated at all, so every stage in that chain drops to near zero. The review also flagged that machine-wide load averages can be misleading since they count threads blocked waiting on the graphics driver, and left behind a small shell snippet for checking true per-core busy time instead of relying on aggregate CPU percentages.
```bash
read_cpu(){ grep -E '^cpu[0-9]' /proc/stat; }
A=$(read_cpu); sleep 10; B=$(read_cpu)
paste <(echo "$A") <(echo "$B") | awk '{
  n=NF/2; t1=0; t2=0; for(i=2;i<=n;i++){t1+=$i; t2+=$(i+n)}
  idle1=$5+$6; idle2=$(5+n)+$(6+n)
  printf "%s busy %5.1f%%\n", $1, 100*((t2-t1)-(idle2-idle1))/(t2-t1) }'
```
