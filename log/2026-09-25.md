# 2026-09-25

A device report retrieval feature wasn't working, and investigating why turned up two blocking issues unrelated to the device itself: a network path problem reaching an intermediate host, and a credential/auth issue in how a background job authenticated to fetch report data. Checking reachability of the intermediate host showed the target port wasn't behaving like the expected protocol, which ruled out a simple key mismatch and pointed to a network-level block instead. Separately, the background job's existing design required holding a long-lived credential to pull report data directly, which was riskier than necessary. Weighed two designs: have the background job call the report source using a short-lived token minted on demand by a central service and restricted to service-to-service calls, versus routing every query back through the central service instead. Went with the short-lived-token approach: added a new endpoint that mints short-lived tokens only for service callers, logs each use with no caching, and tightened access on an existing listing endpoint that had previously been open to any authenticated caller. Updated the background job to consume the new endpoint with a retry-on-expired-token path, reworked the associated tests, and confirmed everything passed. Also ran a full local simulation — standing up the dependent services and posting a synthetic report through the pipeline — to confirm the data still landed correctly in both the database and archive storage.

def fetch_with_fresh_token(get_bearer, call_api):
    token = get_bearer(cached=True)
    response = call_api(token)
    if response.status_code == 401:
        token = get_bearer(cached=False)
        response = call_api(token)
    return response

An automation runner used a single fixed timeout for every step in a multi-step playbook, which didn't fit well when steps had very different expected durations. Added a per-step timeout field to the manifest format, with a fallback to the previous default when a step doesn't specify one, and set values reflecting what each step actually needs — short timeouts for quick network checks, longer ones for steps that involve a device reboot. Verified the updated manifest was accepted by the service that parses it before rolling out the change, and confirmed no other validation logic would reject the new field. Since an older version of that parsing service would reject manifests carrying the new field outright, documented that the service has to be upgraded first, before any bundle using the field gets published. Also found that two related change sets had landed on the wrong branch, fast-forwarded them onto the correct one to keep history consistent, and closed the now-redundant merge request with a note pointing to where the commits ended up.
